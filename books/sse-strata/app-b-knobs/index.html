B.1 引擎 CLI 旋钮（args 数组）

B.1.1 生产里显式设的

旋钮 引擎默认 生产值 作用 调错的症状
--pack — ~/Strata-data/packs/iq3_xxs 权重包目录（专家、profile、tokenizer 都从这里派生） 起不来，strata 直接退出
--native / --ple-gguf — IQ3_XXS 的两个分片（dense + PLE） 常驻 GPU 的 dense 权重与 n-gram 嵌入 显存 OOM / PLE 缺失导致质量崩
--expert-profile — Strata/data/expert-profile.bin 专家路由画像（决定哪些专家常驻） 命中率崩 → 落盘 → 解码掉到个位数 tok/s

--prefill — auto prefill 分块大小（STRATA_PREFILL_AUTO_MAX 决定 auto 上限） 块太大 → 单请求独占 GPU 更久（09 章）

--max-context — 262144 会话总窗口（决定 KV 与各类显存） 调大 → 显存/内存双爆；这是硬约束 1
--kv — int8 KV 精度（fp16 / int8 / q4_0 / k8v4） 降精度省显存但影响长上下文质量

--vision — 开 启用图像（配合 strata-vision sidecar） 关掉 → 图片请求失败
--conversation-cache-slots — 20 停车槽数（12 章第四层） 与 -mib 一起决定能停几条长会话
--conversation-cache-mib 0（关，:440） 8192 停车 RAM 预算 事故 2 的核心：254k 会话快照 4.7 GB → 装两三条就驱逐
--conversation-cache-min-free-mib 2560（:442） 未设（用默认） 低于此空闲就不停车 调高 → 更保守、更少驱逐但更少复用
--vram-reserve-mib 700（:365） 1600 给驱动/其它留的显存 调小 → 链捕获失败 → chain_off 永久降级（10 章）
--ple-io — ram PLE 放主机 RAM（不放 SSD） 换 ssd → 解码期随机读延迟
--pool-workers 0 = 物理核减宿主（:284） 13 CPU 专家池线程数 事故 1：两实例各 24 worker 抢 32 核 → 9.3 tok/s；降 worker 无效、钉核才有效。13 已是上限：taskset 把 lane 钉在 16 核，13 worker + 宿主 = 14 线程已饱和（21.2 的否决记录）
--batch 0（关，:393） 4 serve 一次并行跑几条序列（并发上限在这里） 调大 → 显存与 GMAX 压力；--batch 需要每个 stage 独占一张卡（:4966）
--batch-mtp false（:400） 开 批槽也跑 MTP 链（v1 只对 greedy 槽） 失败会 falling back to one-token windows（:5846）
--batch-groups 1（:399） 1 批分组 需要 layer split 且整除 --batch（:5867）

B.1.2 生产里没设、因此吃默认值的（= 可调空间）

旋钮 默认（行号） 含义 调它会发生什么
--prompt-cache 6（:439） 请求之间保留几个对话检查点，每个约 118 MB 主机 RAM 调大 → 复用更多、RAM 更紧（现 176/216 GiB 悬顶）
--prompt-cache-every 16384（:444） 每 16384 token 打一个检查点 事故 2 的第二环：被驱逐的会话只能靠检查点，密度 16384 → 只救回 16384，其余 ~238k 整段重读。改 4096 → RAM 涨约 4×
--prompt-cache-root 2048（:447） 会话开头的"根"检查点密度 影响第一轮/短会话的复用
--layer-split 未设（dual 布局不用） 按层切到多卡（只配 --serve） split 布局用；与 --peer-device 互斥（:1945）；单卡 split 与停车互斥（:1604–1607）
--peer-device -1（关，:327） 把另一张卡当主从专家缓存层 与 --layer-split、--expert-cache-device1..3 互斥 → 对称共享专家池不可行（19 章已否决表）
--pcie-frac -1 = 按包类型取默认（原生包 0.55）并实测 PCIe 修正（:413、:2064-2077） 未设 未命中专家里由 GPU 经 PCIe 读的比例
--short-read 64（:459；门在 :6547） 未设 不超过 N 个 token 的段走解码窗口读，而不是批处理 prompt 路径（read_windows :6554）
--api-monitor（serve 层，非引擎） 关 每请求内容留存 见 B.3

TTFT 四旋钮（12 章 §12.7、19 章 P1）就是上面这张"没设"表里的三个 + 停车预算：
conversation-cache-mib 8192→24000+、prompt-cache-every 16384→4096、普道准入、组装预算封顶。
四个都只改配置不改代码，但都要重启那条 lane（6–13 分钟）。

B.1.3 编译期常量：不是旋钮，但决定天花板

这五个数字改不了（除非重编），但排查"为什么快不起来"时必须先看它们：

常量 值 位置 它卡住了什么

kVerifyMaxT 8 include/strata/kernels/verify_kernels.hpp:28（iq_kernels.cu:1804 是它的注释引用） 一帧总行数上限；L_max = min(4, 8/S) 的来源（10 章 §10.8）

MAXT 8 src/kernels/cpu/kq_avx2.cpp:43、include/strata/kernels/cpu/expert.hpp:169 CPU 池一次能处理的 token 数

B.7 本附录小结

  • 两条 lane 的引擎 args 完全相同，差异只在二进制、CWD、日志路径、gpu、port ——
    所以"快道更快"不是引擎参数不同，而是车道分工与钉核（11 章、15 章）。
  • 真正没设过的旋钮只有四个：prompt-cache / prompt-cache-every / prompt-cache-root /
    conversation-cache-min-free-mib（外加把 conversation-cache-mib 从 8192 往上抬）。
    它们就是 19 章 P1 的全部内容 —— 配置级改动，但要停服窗口。
  • fit_max_tokens 在 ssebed 的 strata-b.json 里缺失：切 B 到 ssebed 会顺手改掉超窗行为，切换时要一起核对。
  • 网关配置里 rag_enabled=false 让一整族检索旋钮处于休眠；重新启用前先确认窗口预算与 max_context 一致。
  • 引擎那 60+ 个 STRATA_* kernel 开关不属于运维面：它们改的是数值实现，必须过 parity 测试。
