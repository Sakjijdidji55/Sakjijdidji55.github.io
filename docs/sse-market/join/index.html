08 招聘：双选、答辩与席位

5 分钟读完 · 1,997 字

从「投简历」到「坐到圆桌上」的全流程：岗位报名、部门双选、三级答辩、席位与候补、公示与名人堂。规则比代码多，状态机是核心。

仓库：github.com/SysuMirror/join（TypeScript，server/ 约 1 万行，web/ Vue 3）。

身份与入职

① 三级身份

层级 获得方式 含义
集市开发者 UniSSO 登录即得 有账号、能浏览
项目开发者 报名 → 部门双选 → 本人确认 归属某个部门
圆桌成员 三级答辩通过 + 有席位 参与技术部决策
  • 实现：用户表用 developer_level 区分（none / project / roundtable），primary_department_id 记录归属部门，status 区分在职与退出。
  • 坑：部门通过后必须有一次「本人确认」。少了这一步，学生会在不知情的情况下被计入某部门，后面答辩与席位统计全部失真。

② 发起答辩的前置条件

  • 用户操作：个人主页点「发起技术部答辩」。
  • 实现：五道前置校验，任何一条不满足都给出具体原因，笼统的「无权限」不算反馈。
// server/src/services/defense.ts
export function canInitiateDefense(user: UserRow): { ok: boolean; reason: string; department?: DepartmentRow } {
  if (user.status !== 'active') return { ok: false, reason: '账号已退出开发者体系' };
  if (user.developer_level === 'roundtable') {
    return { ok: false, reason: '你已经是圆桌开发者（技术部成员）' };
  }
  if (user.developer_level !== 'project') {
    return { ok: false, reason: '需先通过部门双选成为项目开发者，才能发起技术部答辩' };
  }
  if (!user.primary_department_id) {
    return { ok: false, reason: '尚未归属任何部门，请先完成部门双选' };
  }
  const dept = db.getStore().departments.find((d) => d.id === user.primary_department_id);
  if (!dept) return { ok: false, reason: '所属部门不存在，请联系管理员' };
  const active = activeDefenseOf(user.id);
  if (active) return { ok: false, reason: `你已有一场进行中的答辩（#${active.id}）` };
  return { ok: true, reason: '', department: dept };
}
  • 坑：必须校验「没有进行中的答辩」。只校验等级，用户可以并发发起多场，评审人会被重复派单。

③ 岗位与报名

  • 用户操作：按关键词 / 部门 / 方向 / 类型 / 地点筛选 → 看详情 → 登录后报名。
  • 实现：routes/jobs.ts 提供列表与详情，报名写入 applications，状态从 pending 起。
GET  /api/jobs            列表（keyword / dept / direction / type / location）
GET  /api/jobs/:id        详情
POST /api/jobs/:id/apply  报名（需登录）
GET  /api/me/applications 我的报名
  • 坑：同一人对同一部门只允许一条有效报名。用唯一索引 (user_id, dept_id) 挡重复，不要靠业务判断。

④ 部门双选

  • 用户操作：部门管理员看到报名 → 约沟通（记录时间、动机、投入）或直接通过 → 学生端出现「待确认」→ 确认后进组。
  • 实现：状态机 pending → contacted → passed → confirmed，任一步可 rejected；确认时把 primary_department_id 写回用户。
pending     已报名
contacted   已沟通（记录沟通时间与备注）
passed      部门通过，等待本人确认
confirmed   本人确认，写入部门归属
  • 坑：多个部门同时 passed 时，学生确认一个，其余必须自动失效。否则一个人会同时出现在多个部门名单里。

三级答辩

① 一级：本部门陈述

  • 谁评：本部门负责人。
  • 做什么：陈述事实（做了什么、投入多少），回避打分 —— 本部门对自己成员打分不具备区分度，只提交事实与意见。
  • 实现：createDefense 建答辩记录并生成一级评审任务；一级提交后才允许推进。
defense.status: level1 → level2 → level3 → passed / rejected / waitlist

② 二级：跨部门交叉评审

  • 谁评：其他部门的负责人，自动排除本部门负责人、本部门管理员与一级陈述人。
  • 判定规则（与人数相关）：
// server/src/services/defense.ts
function level2Verdict(defenseId: number): { ready: boolean; pass: boolean; note: string } {
  const reviews = db.getStore().defense_reviews.filter((r) => r.defense_id === defenseId && r.level === 2);
  const done = submitted(reviews);
  const needed = Math.min(2, Math.max(1, reviews.length));
  if (done.length < needed) return { ready: false, pass: false, note: '' };

  const approvals = done.filter((r) => r.decision === 'approve').length;
  const rejects = done.filter((r) => r.decision === 'reject').length;
  const avg = avgScore(done);
  const needApprovals = reviews.length === 1 ? 1 : 2;
  const pass = rejects === 0 && approvals >= needApprovals && (avg === null || avg >= 60);
  const note = `交叉评审 ${done.length}/${reviews.length} 人提交：赞成 ${approvals}，反对 ${rejects}${
    avg === null ? '' : `，平均分 ${avg.toFixed(1)}`
  }`;
  return { ready: true, pass, note };
}
  • 面试点：判定规则里 needed 取 min(2, max(1, 评审人数))，是为了兼容「只派出 1 位评审」的小规模场景 —— 此时 1 票即可定论；派 2 人以上时则要求 2 票赞成。
  • 坑：一票否决（rejects === 0）不能省。只要求「赞成票够」，两个评审一个赞成一个反对也能通过，交叉评审就失去意义。

③ 三级：资源方评审

  • 谁评：资源方代表，评估资源分配主张是否合理。
  • 判定：至少 1 人提交、无人反对、至少 1 票赞成、平均分 ≥ 60；缺席由超管代行。
/** 三级评审汇总：资源方代表至少 1 人提交；无人反对、至少 1 票赞成、平均分 >= 60 */

④ 状态推进

  • 实现：advanceDefense 是纯推进函数 —— 看当前级别、检查该级是否「可定论」，可定论则推进或终结。不可定论直接返回，不改状态。
// server/src/services/defense.ts
export function advanceDefense(defense: DefenseRow): void {
  const s = db.getStore();
  const applicant = s.users.find((u) => u.id === defense.applicant_user_id);
  const dept = s.departments.find((d) => d.id === defense.department_id);
  if (!applicant || !dept) return;

  if (defense.status === 'level1' || defense.status === 'submitted') {
    const level1 = s.defense_reviews.filter((r) => r.defense_id === defense.id && r.level === 1);
    if (!submitted(level1).length) return;          // 一级没交，停在这里
    defense.status = 'level2';
    defense.current_level = 2;
    ensureLevel2Reviews(defense, applicant, dept);  // 生成二级评审任务
    return;
  }

  if (defense.status === 'level2') {
    ensureLevel2Reviews(defense, applicant, dept);
    const verdict = level2Verdict(defense.id);
    if (!verdict.ready) return;
    if (!verdict.pass) {
      finalizeReject(defense, `二级交叉评审未通过。${verdict.note}`, '评审团');
      return;
    }
    defense.status = 'level3';
    defense.current_level = 3;
    defense.final_note = verdict.note;
    ensureLevel3Reviews(defense, applicant, dept);
  }
}
  • 坑：advanceDefense 必须幂等。评审提交、管理员刷新、定时任务都可能触发它，重复调用不能生成重复的评审任务（ensureLevel2Reviews 内部要查重）。

⑤ 强制裁决与撤回

  • 实现：forceDecide 供超管在极端情况（评审长期不提交、评审人离职）下直接定论，并记录原因；canSubmitReview / canViewDefense 控制谁能看、谁能评。
export function forceDecide(...)   // 超管强制裁决，写原因
export function canSubmitReview(...)  // 校验评审人资格与是否已提交
export function canViewDefense(...)   // 申请人与评审人可看，其余不可见
  • 坑：强制裁决必须写审计（谁、为什么）。没有原因的强制通过，是这类系统里最难解释的操作。

席位与候补

① 席位构成

部门席位 = 保底（≥1） + 浮动（按部门规模与资源贡献分配）
  • 实现：departmentSeatStats(dept) 返回 total / occupied / available；答辩通过时先看 available，有位置直接进圆桌，没有则进候补。

② 自动递补

  • 实现：promoteWaitlist 循环取「该部门候补中 id 最小（即最早进入候补）」的一条，晋升为圆桌，直到没有空位或没有候补。
export function promoteWaitlist(departmentId: number): number {
  const s = db.getStore();
  const dept = s.departments.find((d) => d.id === departmentId);
  if (!dept) return 0;
  let promoted = 0;
  while (true) {
    const stats = departmentSeatStats(dept);
    if (stats.available <= 0) break;
    const next = s.defenses
      .filter((d) => d.department_id === departmentId && d.status === 'waitlist')
      .sort((a, b) => a.id - b.id)[0];
    if (!next) break;
    finalizePass(next, '席位释放，按候补顺序递补进入圆桌', '席位递补');
    promoted += 1;
  }
  return promoted;
}
  • 坑：递补按 id 升序（即答辩通过先后），不按报名时间。按报名时间排会让后来者插到早就通过答辩的人前面。
  • 面试点：while 循环里每轮都重新算 available，一次算好再减的话，finalizePass 内部再占用席位就会超发。

③ 席位复核

  • 实现：recordSeatReview 记录席位复核；releaseRoundtableSeat 释放某人的圆桌席位并触发递补。
export function releaseRoundtableSeat(...)  // 释放席位 → promoteWaitlist

管理与通知

① 角色化后台

  • 用户操作：不同角色进 /admin 看到的标签页不同。
  • 实现：超管看全部；部门管理员只看本部门；资源方代表只开放三级评审与被指派任务。接口层独立鉴权。
/admin  按角色渲染：超管 / 部门管理员 / 资源方代表
  • 坑：前端隐藏标签只影响可见性。每个管理接口都要独立校验角色，否则直接调接口即可越权。

② 邮件通知

  • 实现：services/mail.ts 在报名、通过、答辩指派、公示等节点发信；模板与收件人按节点确定。

  • 坑：邮件发送必须异步且可失败重试。同步发信一旦 SMTP 超时，会把整个请求拖死。

③ 数据存储

  • 实现：当前用 JSON 存储（db.getStore()），db.ts 负责初始化、种子数据与就绪检查；适合「一年改几次」的数据规模，迁移成本低。

招聘 · 面试速答

  • 三级身份：集市开发者（登录即得）→ 项目开发者（双选 + 本人确认）→ 圆桌（答辩 + 席位）。
  • 答辩前置：在职、非圆桌、已是项目开发者、有归属部门、无进行中答辩。
  • 二级判定：needed = min(2, max(1, 人数))；无反对 + 赞成数达 needApprovals + 均分 ≥ 60。
  • 三级判定：至少 1 人提交、无反对、≥ 1 赞成、均分 ≥ 60。
  • 席位：保底 ≥1 + 浮动；无位进候补，释放后按答辩通过顺序自动递补，循环内重算余量。
  • 公示：由数据生成 + PDF 导出，手改会导致状态分叉。
