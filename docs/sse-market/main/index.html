02 主站：账号、帖子与互动

16 分钟读完 · 6,911 字

前端：https://gitee.com/qvq-qiu/newSSE、后端：https://gitee.com/yang-peiyue/SSE_market_server

账号与安全

① 注册

  • 用户操作：在 sso.ssemarket.cn/register 填邮箱 → 收 6 位验证码 → 设密码（可填激活码 CDKey）→ 提交。
  • 入口位置：主站 POST /api/auth/register 只接受 UniSSO 的服务端调用，浏览器直接调用返回 403。绕过 UniSSO 创建的账号在统一身份中不存在，无法再次登录，因此注册统一在 sso.ssemarket.cn/register 完成。
  • 实现链路：前端把密码用 SM2 加密 → 主站解密 → 校验两次一致、长度 ≥6 → 交给 service.Users.Register 校验验证码/CDKey、查重（邮箱唯一、手机号唯一）→ 落库 → 返回 access + refresh。若当前 SSO 模式开启，再用刚设的密码向 UniSSO 换一次共享会话，失败也不影响注册结果。
// controller/userController.go —— 只拦浏览器，不拦 UniSSO 的服务端调用
func Register(c *gin.Context) {
	if browserAuthRequest(c) {
		response.Response(c, http.StatusForbidden, 403, nil,
			"注册请前往统一身份认证：https://sso.ssemarket.cn/register")
		return
	}
	password1 := util.Decrypt(requestUser.Password) // 前端 SM2 密文
	password2 := util.Decrypt(requestUser.Password2)
	if len(password2) < 6 { /* 422 密码不能少于6位 */ }
	if password1 != password2 { /* 422 两次密码不相同 */ }

	tokens, err := service.Users.Register(c.Request.Context(), domain.RegisterInput{
		Name: requestUser.Name, Phone: requestUser.Phone,
		Email: strings.TrimSpace(requestUser.Email),
		Password: password1, ValiCode: requestUser.ValiCode, CDKey: requestUser.CDKey,
	})
	if errors.Is(err, domain.ErrConflict) { /* 422 该邮箱/手机号已存在 */ }
	if errors.Is(err, domain.ErrUnauthorized) { /* 400 验证码错误 */ }
	// 其余分支与错误处理略（见仓库）
}
  • 坑：browserAuthRequest 靠 Origin/Referer 判断，服务端调用天然没有这两个头 —— 所以能精确区分「浏览器乱调」和「UniSSO 正常建号」，不用加白名单。
  • 面试点：注册需保证幂等。邮箱唯一索引是最终约束，业务层的「先查再插」在并发下会产生重复插入。

② 登录

  • 用户操作：输邮箱 + 密码，或点「集市账号登录」跳 UniSSO。
  • 关键变化：密码不由主站校验，主站把邮箱密码交给 UniSSO 的密码校验接口，拿回身份后再签发自己的 token。这是「一个账号中心」的代价，也是收益 —— 改密码、封号、二次验证全在 UniSSO 一处生效。
  • 错误码按失败原因分别定义：
情况 状态码 提示
密码错 401 邮箱或密码错误
非学院内部成员 403 该账号没有软件工程学院内部权限
该身份已绑其他集市账号 409 该统一身份已绑定其他集市账号
邮箱没有集市账号 422 请先注册
密码校验被禁 403 不允许通过密码校验登录
失败次数过多 429 已被临时锁定，请 15 分钟后再试
UniSSO 挂了 503 统一身份服务暂时不可用 
// controller/userController.go
func Login(c *gin.Context) {
	mode := service.CurrentSsoMode()
	if mode == service.SsoModeDisabled { /* 503 统一身份服务暂时不可用 */ }

	email := requestUser.Email
	password := util.Decrypt(requestUser.Password) // 健康探测只给状态提示，密码始终由 UniSSO 校验
	tokens, ssoSess, err := service.Sso.LoginViaUnisso(c.Request.Context(), email, password)
	if err != nil {
		switch {
		case errors.Is(err, service.ErrSsoBadCredentials):  /* 401 */
		case errors.Is(err, service.ErrSsoForbidden):       /* 403 非内部成员 */
		case errors.Is(err, service.ErrSsoConflict):        /* 409 已绑其他账号 */
		case errors.Is(err, service.ErrSsoNoLocalAccount):  /* 422 请先注册 */
		case errors.Is(err, service.ErrSsoTooManyAttempts): /* 429 锁定 15 分钟 */
		case errors.Is(err, service.ErrSsoUnavailable):     /* 503 */
		}
		return
	}
	service.SsoAudit("unisso_login", "mode", mode, "email", email, "result", "success")
	setSsoCookie(c, ssoSess) // 父域 Cookie，主站/图床/iWiki 共享登录态
	response.Success(c, gin.H{"token": tokens.AccessToken, "refresh_token": tokens.RefreshToken}, "登录成功")
}
  • 坑：setSsoCookie 的名称/值/Domain/有效期全部从 UniSSO 响应里取，不在主站写常量。父域 Cookie 一旦硬编码域名，本地开发与更换域名时都会失效。
  • 面试点：登录失败要审计（SsoAudit 记 mode/email/result），但绝不能记密码和完整 token。审计日志本身就是拖库目标。

③ 鉴权中间件

  • 用户操作：无感知。登录后所有请求自动带 Authorization: Bearer <token>。
  • 实现：三层分工 —— 严格鉴权（必须登录）、可选鉴权（登录了就给身份，游客也放行）、OAuth 鉴权（第三方应用带 scope）。
  • 中间件顺序：先严格鉴权解析出用户，再进入布隆过滤器做防刷判断。
// route/routes.go —— 三组路由，同一批 handler 按需挂不同中间件
auth.Use(middleware.StrictAuthMiddleware())
auth.Use(middleware.BloomFilterMiddleware()) // 布隆过滤器挡恶意刷接口
oauth.Use(middleware.OAuthMiddleware())
noauth.Use(middleware.OptionalAuthMiddleware())

// middleware/authMiddleware.go
tokenString := ctx.GetHeader("Authorization")
if tokenString == "" || len(tokenString) <= 7 || !strings.HasPrefix(tokenString, "Bearer ") {
	ctx.JSON(http.StatusUnauthorized, gin.H{"code": 401, "msg": "权限不足"})
	ctx.Abort()
	return
}
tokenString = tokenString[7:]
token, claims, err := common.ParseToken(tokenString)
  • 坑：OptionalAuthMiddleware 会校验，但校验失败也放行。所以凡是读到用户身份就必须显式判断 nil —— 详情页的「我点过赞没有」就靠这个，游客看到的是未点赞状态。
  • 面试点：校验维度是「用户 × 路径 × 时间窗」，Redis Set 的存储开销不可接受；布隆过滤器以少量假阳性换取常量级内存，假阳性的后果是多拒绝一次请求。

④ 个人访问令牌 PAT

  • 用户操作：设置页创建 PAT（可勾 scope）→ 复制 sk_xq_ 开头的串 → 贴到 MCP 客户端或脚本里。
  • 用途：浏览器之外的调用方（MCP、CI）不能走 Cookie，也不能每次让用户输密码，用长期令牌换身份。
  • 实现：创建时返回一次原文，库里只存哈希；/api/auth/token/verify 供 MCP 网关以 PAT 换身份；吊销与删除分开（吊销保留记录、删除抹掉）。MCP 入口单独限流 30 次/分钟。
// route/routes.go —— MCP 只认 PAT，和 JWT 登录态物理隔离
forumMCP := r.Group("/api/auth")
forumMCP.Use(middleware.ForumPATAuth(), middleware.UserRateLimit("forum-mcp", 30, time.Minute))
forumMCP.Any("/mcp", controller.NewForumMCPHandler())
  • 坑：PAT 的 scope 要能「收窄」不能「放大」。给 MCP 的令牌只授予帖子读写权限，不包含修改密码等能力。
  • 面试点：长期令牌必须有独立吊销通道，且不能与登录态共用签名密钥 —— 否则轮换 JWT 密钥时会把所有 PAT 一起废掉。

⑤ 改密 / 改邮箱 / 注销

  • 用户操作：设置页改密码（验旧密码）、改邮箱（验新邮箱验证码）、注销账号。
  • 实现：改密与改邮箱都要求先验证身份（旧密码 / 邮箱验证码）；改邮箱同时更新唯一索引，冲突直接 422；注销是软删 + 清会话 + 解绑 UniSSO，不物理删数据。
  • 坑：改密后必须让旧 refresh 失效，否则被盗号后攻击者用 refresh 一直续期，改密不生效。
// controller/userController.go
func ModifyPassword(c *gin.Context) { /* 验旧密码 → 更新 → 清 refresh_tokens */ }
func ModifyEmail(c *gin.Context)    { /* 验新邮箱验证码 → 更新 → 唯一索引冲突返回 422 */ }
func DeleteMe(c *gin.Context)       { /* 软删 + 解绑 + 清会话 */ }
  • 面试点：账号系统的三个「必做」—— 改密踢下线、注销软删、操作留审计。

帖子与浏览

① 发帖

  • 用户操作：选分区 → 填标题 → 写 Markdown 正文（可插图片/音乐/视频）→ 可选匿名 → 发布。
  • 实现链路：
    1. 前端先传图，拿 COS 地址，再拼进 Markdown。
    2. 提交走 POST /api/auth/post，后端校验标题长度、正文非空、分区合法。
    3. 匿名帖在读的时候才脱敏，库里仍存真实 user_id —— 否则作者自己都找不回自己的帖子。
    4. 写库成功 → 让列表缓存换 generation → 触发 @解析（含 @小秋）。
  • 关键设计：列表缓存用 generation 版本号，发帖不删缓存，只把版本号 +1，旧 key 自然失效。
// service/browse_feed.go（示意）—— 公共 Feed 带 generation，写入即换代
func (s *BrowseService) InvalidateHomeBrowse() {
	core.MyRedis.Incr(ctx, "post:browse:generation")
}
// 读的时候把 generation 拼进缓存键，换代后自然 miss，不用 SCAN 删旧键
cacheKey := fmt.Sprintf("post:browse:home:%s", gen)
  • 坑：SCAN 遍历键会阻塞单线程 Redis；用版本号或命名空间换代，失效操作为 O(1)。
  • 面试点：匿名不是加密。库里明文存作者，只靠响应层脱敏 —— 一旦有人写个新接口忘了脱敏就泄露，所以要用统一的 anonymizeAuthor 出口。

② 列表与分页

  • 用户操作：首页切「全部/关注/推荐/热榜」，按分区、标签、时间、排序筛选，滚动加载下一页。
  • 实现：一个 BrowseFilter 结构承接所有筛选维度，避免为每种组合写一个接口；缓存按 feed 类型分开，home / history（浏览足迹）/ save（收藏）/ rating（评分专区）各自独立键。
  • 坑：分页用 OFFSET 在深页会全表扫，数据量上来必须换游标（WHERE id < last_id）。
// controller/postController.go
func Browse(c *gin.Context) {
	// searchsort ∈ {home, history, save, rating}，与分区/标签/时间/排序一起组装 BrowseFilter
	filter := domain.BrowseFilter{ /* ... */ }
	list, total, err := service.Posts.Browse(c.Request.Context(), filter)
	// 逐条过匿名脱敏，再返回
}
  • 面试点：total 在大表上的聚合开销较高；可单独维护计数表，或前端不展示总页数、只提供「加载更多」。

③ 详情与浏览数

  • 用户操作：点进帖子 → 看到正文、点赞数、评论、投币数；刷新一次浏览数 +1。
  • 实现：详情整包缓存 post:detail:<id>；浏览数不进 MySQL 同步写，走 Redis INCR + 脏标记，5 秒批量回写。
// service/hot_data_service.go
func (s *HotDataService) IncrBrowseCount(postID int) int64 {
	if !s.redisHealthy {
		return s.browseNumFromDB(postID) // Redis 挂了直接降级查库
	}
	s.ensureBrowseCountKeySeeded(postID) // 首次从 DB 播种，避免从 0 开始
	n, err := core.MyRedis.Incr(ctx, util.GetPostBrowseCountKey(postID)).Result()
	if err != nil {
		return s.browseNumFromDB(postID)
	}
	s.browseDirty.Store(postID, time.Now()) // 打脏标记，后台每 5s 批量落库
	return n
}
  • 坑：播种（seed）这一步不能省。如果 key 不存在直接 INCR，浏览数会从 1 开始，把历史数据「清零」。
  • 面试点：浏览数这种高写低读的计数，一定要「缓存为准 + 定期回写」，直接 UPDATE ... SET num = num + 1 会把行锁打爆。

④ 点赞 / 收藏 / 关注 / 置顶 / 私密 / 删除

  • 用户操作：帖子卡片或详情页点图标，状态即时翻转；作者可置顶、设私密、删除；他人可举报。
  • 实现：点赞是关系表 + 计数两处写，同一事务；收藏进「我的收藏」独立表；关注帖子单独一张表（区别于关注作者）；私密只改可见性不删数据；删除是软删 + 从所有 feed 移除。
  • 统一规则：任何改变详情内容的写操作，都必须失效 post:detail:<id> —— 点赞数、评论数、投币数都在这个缓存里。
// controller/postController.go
func UpdateLike(c *gin.Context)        { /* 关系表翻转 + 计数 ±1 + 失效详情缓存 */ }
func UpdateSave(c *gin.Context)        { /* 收藏表增删 + 失效个人收藏列表 */ }
func ToggleWatch(c *gin.Context)       { /* 关注帖子，独立于关注作者 */ }
func UpdatePostPrivacy(c *gin.Context) { /* 只改 visible，不删数据 */ }
  • 坑：点赞和取消点赞会来回打，计数用 ±1 在并发下会漂。要么用唯一索引 + 计数表重算，要么接受微小误差并定期校准。
  • 面试点：软删的代价是所有查询都要带 deleted_at IS NULL，一旦漏一处就会「删了还能搜到」。由 GORM 的软删钩子统一处理。

⑤ 搜索与热榜

  • 用户操作：顶部搜索框搜帖子/用户，热榜看当前最热内容。
  • 实现：搜索走标题 + 正文匹配，服务端二次过滤可见性（私密帖不能出现在别人结果里）；热榜分数离线算好，不随请求实时排序。
  • 热度公式（CalculateHeat）：赞 +3、浏览 +1、评论 +6，删评论按 0.5^days 衰减。
// controller/postController.go
func CalculateHeat(c *gin.Context) { /* 赞*3 + 浏览*1 + 评论*6，删评论按 0.5^days 衰减 */ }
  • 坑：搜索结果的权限过滤必须在服务端做。前端过滤会先把私密内容下发到浏览器，过滤必须放在服务端。
  • 面试点：热榜按「时间衰减 + 互动加权」算分，纯计数会让老帖永远占榜。

评论与评分

① 一级评论

  • 用户操作：帖子底部输入框写评论 → 提交 → 立刻出现在列表顶部。
  • 校验顺序（顺序本身就是设计）：内容非空 → 长度 ≤1000 字（按 rune 算，不是 byte）→ 用户身份 → 是否被禁言 → 帖子是否存在。
// controller/commentController.go
func PostPcomment(c *gin.Context) {
	if len(msg.Content) == 0 { /* 400 评论内容不能为空 */ }
	if utf8.RuneCountInString(msg.Content) > 1000 { /* 400 评论内容过长 */ }
	user, ok := requireViewerLegacyPhone(c, msg.UserTelephone)
	if !ok { /* 422 权限不足 */ }
	if user.BanEnd.After(time.Now()) { /* 400 你尚处于禁言状态中，不得评论 */ }

	result, err := service.Comments.CreatePcomment(c.Request.Context(), domain.PcommentCreateInput{
		UserID: user.ID, PostID: msg.PostID,
		Content: msg.Content, AsStaffUserID: msg.AsStaffUserID, // 支持以职位身份发言
	})
}
  • 坑：len(content) 算的是字节，一个中文 3 字节，用它会变成 333 字就报超长。必须 utf8.RuneCountInString。
  • 面试点：限流与禁言要分开 —— 限流是「太快」，禁言是「不许」。禁言用户返回 400；429 表示请求过快，语义不对。

② 楼中楼回复

  • 用户操作：在别人评论下点「回复」→ 输入 → 出现在该评论下方。
  • 实现：二级评论单独一张 ccomment 表，带 parent_id 指向一级评论；列表接口把两级拼成树，只查当前页的一级评论再批量捞二级，避免 N+1。
// controller/commentController.go
func PostCcomment(c *gin.Context) { /* 二级回复，parent 指向 pcomment */ }
  • 坑：楼中楼只做两层，不做无限嵌套。三层以上前端渲染和分页都会失控，回复三层统一挂到二级下面并 @ 被回复人。

③ 点赞 / 点踩 / 删除评论

  • 用户操作：评论右侧点赞、点踩、删除（仅作者或管理员）。
  • 实现：赞与踩互斥，切换时要把另一侧减掉；删除一级评论时二级一起失效；每次写操作失效评论列表缓存 comment:list:<postID>:<type>。
func UpdatePcommentLike(c *gin.Context) { /* 赞/踩互斥，切换时反向 -1 */ }
func UpdatePcommentDeny(c *gin.Context) { }
func DeletePcomment(c *gin.Context)     { /* 级联失效二级 + 缓存 */ }
  • 面试点：赞踩互斥如果用两张表，必须在一个事务里改；用一张表存 -1/0/1 更简单。

④ 评分专区

  • 用户操作：进「打分」页 → 选分类 → 发评分贴 → 给星级 → 别人可评论、点赞。
  • 实现：完全独立的一套表，不复用评论表。链路是：分类 → 评分贴 → 星级提交（每人每帖一次）→ 评分评论。
  • 独立建表的原因：评分有「一人一票」「星级聚合」等约束，复用通用评论表需额外字段，且无法建立对应唯一索引。
// controller/rating_controller.go

@ 提及

主站有三种 @，实现机制各不相同。

① @ 用户

  • 用户操作：正文里打 @ → 弹候选下拉 → 选中某人 → 发布后名字变成可点链接。
  • 难点：Markdown 正文为纯文本，@张三 之后可能紧跟标点、中文或 HTML 标签，需要确定昵称的结束位置。
  • 解法：编辑期只记录候选；渲染期拿「已知用户表」按昵称长度降序做最长前缀匹配，命中后再做边界判定（空白/标点/CJK/HTML 标签）。
  • 输入期的容错：用户可能打 @张三，你好，所以提交时要生成「剥尾部标点」的变体一起拿去解析。
// newSSE/src/utils/mention.ts —— 生成候选变体：原名 + 逐字符剥标点
export function mentionCandidates(captured: string): string[] {
  const cur = captured.trim()
  if (!cur) return []
  const set = new Set<string>([cur])
  for (let i = 0; i < cur.length; i++) {
    if (PUNCT_RE.test(cur[i])) {
      set.add(cur.slice(0, i))      // "@张三，你好" → "@张三"
      set.add(cur.slice(0, i + 1))  // 也保留带标点的版本
    }
  }
  return [...set].filter(Boolean).sort((a, b) => b.length - a.length) // 长的优先
}

① 心跳上报

  • 用户操作：无感知。登录后页面每 60 秒自动发一次心跳，切到后台暂停，切回前台立刻补一次。

④ 年度报告 / 主题皮肤

① 商城

  • 用户操作：发布商品（图 + 价 + 描述）→ 列表浏览 → 详情 → 下架/删除 → 标记已售出。
  • 实现：常规 CRUD + COS 图片；首页轮播图从「在售 + 有图」的商品里取。

② 简历

  • 用户操作：上传简历（PDF/图片）→ 列表 → 在线预览 → 下载 → 更新 → 删除。每人最多 5 份。
  • 实现：文件存 COS；预览只下发一个 30 分钟有效的临时 URL，永久直链不下发；下载接口挂 OptionalAuth，允许「登录态 Bearer」和「签名链接」二者校验其一。

管理端

① 登录

  • 用户操作：管理端只能用 UniSSO 登录，且必须是学院成员 + 在白名单里。

  • 实现：管理员 token 单独签发，有效期 1 天，短于用户 token 的 7 天，并与用户 token 隔离；用户 token 调用管理接口返回 401。

  • 面试点：管理员与用户凭证在服务端隔离；共用一套会使「用户 token 泄露」直接影响后台写入权限。

② 成员管理

  • 用户操作：搜索用户 → 改资料 → 封禁 / 禁言 / 解禁 → 看禁言名单。
  • 实现：封禁是 ban_end 时间戳（不是布尔值），到期自动恢复，不用定时任务去解封。
// 权限判定统一看时间戳，过期即视为未封禁
if user.BanEnd.After(time.Now()) { /* 仍在禁言/封禁中 */ }
  • 坑：用布尔值 is_banned 就必须有定时任务解封，任务一挂就永远封着。时间戳方案天然自愈。

③ 内容治理

  • 用户操作：帖子审核（违规/不违规）→ 删帖 / 加精 / 取消加精 → 处理举报 → 处理反馈。
  • 实现：审核与举报联动 —— 举报成立后自动走 MarkViolation：结案 + 惩罚作者 + 通知作者 + 通知举报人，一次事务里全做完。
// service/sue_service.go
func (s *sueService) MarkViolation(ctx context.Context, sueID int) error {
	sue, err := s.sues.FindByID(ctx, sueID)
	_ = s.sues.MarkFinishedByID(ctx, sueID, sueStatusViolation)
	_ = s.sues.MarkFinishedByTarget(ctx, sue.TargetType, sue.TargetID, sueStatusViolation)
	result, err := s.sues.ProcessViolation(ctx, sue) // 算惩罚（禁言时长等）
	user, err := s.sues.PunishUser(ctx, result.TargetUserID)
	punishText := fmt.Sprintf("你的%s[%s]内容涉嫌违规被举报…", result.SueType, result.Content, user.BanEnd.Format(...))
	_ = s.sues.CreateNotice(ctx, result.TargetUserID, "punish", punishText, result.SueID)
	return s.sues.CreateNotice(ctx, result.ReporterID, "sue", "我们已经收到你的举报…", result.SueID)
}
  • 坑：通知要同时发给被罚者和举报人。只通知被罚者，举报人不知道结果，下次就不举报了。
  • 面试点：同一目标的多条举报由 MarkFinishedByTarget 一次结案，避免逐条重复处理。

④ 推荐流灰度 / OAuth 应用 / 视频 / 博客 / CDKey / 数据看板

  • 用户操作：管理页里切推荐算法模式、管第三方应用、管视频、发博客、发激活码、看数据看板。
  • 实现：推荐流的模式是配置项，可实时切（effectiveMode），不用发版；OAuth 应用管理控制哪些第三方能拿用户身份；CDKey 是注册激活码，一次性使用。
// service/recommendation_service.go
func effectiveMode(cfg domain.RecommendConfig) string {
	if cfg.Mode == "" { return domain.RecommendModeDefault } // 兜底，配置缺失不至于 500
	return cfg.Mode
}
  • 面试点：灰度开关要有默认值兜底。配置中心挂了、字段没填，服务不能跟着挂。

主站 · 面试速答

  • 鉴权：用户 JWT 7 天 / 管理员 JWT 1 天 / OAuth2 access 5 分钟，三套物理隔离；另加 PAT（sk_xq_）给 MCP，入口单独限流 30 次/分。
  • 登录：密码由 UniSSO 校验，主站只负责换发自己的 token 并种父域 Cookie；错误码细分到 401/403/409/422/429/503。
  • 缓存：列表用 generation 版本号整体换代（O(1)），详情用主动失效，浏览数用脏标记 5 秒批量回写。
  • 在线：ZSET 滑动窗口 150 秒，双键（全站 + 场景），单次 Pipeline 完成清理与计数，切场景要 ZREM 旧键。
  • 投币：唯一索引兜住每人每内容 ≤2，单事务五步，取消以投币记录为凭证（不要求目标存在）。
  • @ 三种：@用户是渲染期最长前缀匹配；@小秋是 goroutine + context.Background() + 双层去重；@职位身份是真实身份与展示身份分离。
  • WebSocket：token 走 query（原生客户端带不了 Header），先落库再推送，未读用「计数键 + 索引集合」两件套。
  • 热度：赞 +3 / 浏览 +1 / 评论 +6，删评论按 0.5^days 衰减。
  • 封禁：存 ban_end 时间戳，到期自动生效，不依赖定时任务；布尔值做不到这点。
