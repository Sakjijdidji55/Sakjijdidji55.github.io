05 UniSSO：统一身份

6 分钟读完 · 2,451 字

全生态的账号中心：注册、登录、扫码、二次验证、OAuth2/OIDC 授权、应用与授权管理。C++20 + cpp-httplib，会话存 Redis，令牌内部用 HMAC JWT、对外 OIDC 用 RSA（JWKS 暴露公钥）。

仓库：github.com/SysuMirror/unisso（backend/src 约 1.3 万行 C++，frontend/ Vue 3）。

注册与登录

① 注册

  • 用户操作：填邮箱 → 收 6 位验证码 → 设密码 → 提交 → 邮箱验证后可用。
  • 实现：
    1. 验证码不落明文，落库前用服务端密钥 HMAC-SHA256 后存 Redis；待注册记录按「邮箱摘要」建键。
    2. 发送频率双重限流：同一邮箱每小时上限、同一 IP 每小时上限。
    3. 提交后进入待验证态，验证通过才建正式用户。
  • 关键代码
// backend/src/app/registration.cpp
std::string pendingKey(const std::string& email) {
    return "registration_pending:" + digestEmail(email);
}

std::string codeHash(const std::string& code) {
    auto& cfg = AppConfig::get();
    std::string key = cfg.secretKey.empty() ? cfg.signingKeyId : cfg.secretKey;
    return util::hex(util::hmacSha256Raw(key, code));
}

std::string randomCode() {
    static std::atomic<unsigned int> counter{0};
    std::random_device rd;
    unsigned int value = rd() + counter.fetch_add(1);
    return std::to_string(100000 + (value % 900000));   // 固定 6 位
}

bool rateLimited(const std::string& email, const std::string& ip) {
    std::string digest = digestEmail(email);
    long long emailCount = Cache::incr("registration_email_hour:" + digest, 3600);
    ...
}
  • 坑：验证码比对必须是「哈希后常数时间比较」。直接比明文，Redis 泄露等于验证码泄露；用普通 == 比较，理论上存在时序侧信道。
  • 坑：限流键用「邮箱摘要」；用原文会把用户邮箱写进 Redis 键名，运维 KEYS * 就能看到全站邮箱。

② 登录

  • 用户操作：邮箱（或用户名）+ 密码登录；也可以点「集市账号登录」。
  • 实现：
    1. 先查锁定状态，未过锁定期直接 429。
    2. 本地校验密码（bcrypt）；失败且开启了集市通道时，回退到集市（SSE）校验 —— 集市凭证一定是邮箱，所以用户名登录不走回退。
    3. 通过后建会话、种父域 Cookie。
  • 关键代码
// backend/src/app/handlers_auth.cpp
void authLogin(const Request& req, Response& res) {
    // "email" 字段同时接受邮箱与用户名；锁定与限流按提交的标识计算
    std::string identifier = util::trim(http::input(req, "email"));
    std::string email = util::lower(identifier);
    std::string password = http::input(req, "password");
    std::string next = safeNextUrl(http::input(req, "next"));
    std::string ip = http::clientIp(req);

    long long lockedUntil = 0;
    if (isLocked(email, ip, lockedUntil)) {
        http::error(res, 429, "too_many_attempts", "登录尝试次数过多，请 15 分钟后再试");
        return;
    }
    auto user = identifier.find('@') == std::string::npos
        ? repo::findUserByUsername(identifier)
        : repo::findUserByEmail(email);
    bool authenticated = user && user->isActive && password::verify(password, user->passwordHash);

    // 本地无此账号或密码不匹配时，若开启集市通道且标识是邮箱，回退到集市校验
    if (!authenticated && AppConfig::get().sseEnabled && email.find('@') != std::string::npos) {
        ...
    }
}
  • 坑：next 参数必须校验为站内相对路径（safeNextUrl），否则登录页会成为开放重定向跳板。
  • 面试点：锁定键同时包含邮箱和 IP。只按邮箱锁，攻击者可以拿一个邮箱把别人锁死；只按 IP 锁，分布式换 IP 即可绕过。

③ 邮箱验证与重发

  • 用户操作：注册后点邮件里的链接 / 填验证码完成验证；没收到可重发。
  • 实现：/api/auth/verify-email 校验并置 email_verified；/api/auth/resend-registration 重发，同样受限流约束。
// 路由（backend/src/app/routes.cpp）
app.post("/api/auth/register", handlers::authRegister);
app.post("/api/auth/verify-email", handlers::authVerify);
app.post("/api/auth/resend-registration", handlers::authResend);

④ 找回密码

  • 用户操作：输邮箱 → 收验证码 → 设新密码。
  • 实现：两段式接口，start 只发码不泄露账号是否存在，confirm 校验码后改密并清理该用户现有会话。
app.post("/api/auth/password-reset/start", handlers::passwordResetStart);
app.post("/api/auth/password-reset/confirm", handlers::passwordResetConfirm);
  • 坑：start 必须对所有邮箱返回同样的响应。账号是否存在若能从响应区分，就成了账号枚举接口。

⑤ 登出、当前用户、会话查询

  • 实现：authLogout 删会话并清 Cookie；authMe 返回用户 JSON；authSession 返回会话摘要。
// backend/src/app/handlers_auth.cpp
void authMe(const Request& req, Response& res) {
    auto user = authx::currentUser(req);
    if (!user) { http::error(res, 401, "authentication_required", "未登录"); return; }
    std::map<std::string, JsonValue> obj;
    obj["user"] = repo::userJson(*user, true);
    http::json(res, 200, JsonValue(obj));
}

⑥ CSRF 令牌

  • 实现：GET /api/csrf-token 下发一次性令牌，写操作校验；浏览器端与 Cookie 双提交配合。
app.get("/api/csrf-token", handlers::csrfToken);

扫码登录

① 生成与轮询

  • 用户操作：PC 打开登录页出现二维码，手机扫码后确认，PC 自动登录。
  • 实现：qr/start 生成二维码记录（Cache 带 TTL），qr/poll 轮询状态；二维码 ID 有格式校验，防止被当作任意键读写。
app.get("/api/auth/qr/start", handlers::qrLoginStart);
app.get("/api/auth/qr/poll", handlers::qrLoginPoll);
app.get("/api/auth/qr/scan", handlers::qrLoginScan);
app.get("/api/auth/qr/detail", handlers::qrLoginDetail);
app.post("/api/auth/qr/confirm", handlers::qrLoginConfirm);
app.post("/api/auth/qr/deny", handlers::qrLoginDeny);

② 手机端确认

  • 用户操作：手机（已登录）扫码 → 看到登录设备与地点 → 点确认 / 拒绝。
  • 实现：确认接口要求手机端已登录；同一用户每分钟决策次数有上限；二维码已被他人处理时返回 409，不覆盖他人操作。
// backend/src/app/handlers_qrlogin.cpp
void qrLoginConfirm(const Request& req, Response& res) {
    User user;
    if (!authx::requireUser(req, res, user)) return;
    std::string id = util::trim(http::input(req, "id"));
    if (!validQrId(id)) { http::error(res, 400, "invalid_id", "二维码参数不正确"); return; }

    long long decides = Cache::incr("qr_login_decide:" + user.id, 60);
    if (decides > 20) { http::error(res, 429, "rate_limited", "操作过于频繁，请稍后再试"); return; }

    std::map<std::string, JsonValue> rec;
    if (!loadRecord(id, rec)) { http::error(res, 410, "qr_expired", "二维码已过期，请回到电脑上刷新"); return; }
    std::string status = statusOf(rec);
    if (status == "confirmed") {
        if (jsonx::getString(rec, "user_id") == user.id) { http::ok(res); return; }
        http::error(res, 409, "already_handled", "这个二维码已在其他设备上处理");
        return;
    }
    if (status == "denied") { http::error(res, 409, "already_denied", "这个二维码已被拒绝"); return; }
    ...
}
  • 坑：确认接口要按「用户」限流，不能只按二维码 ID。否则一张二维码被反复确认/拒绝，状态机被打乱。
  • 面试点：二维码过期返回 410；404 表示不存在，前端据此区分「过期」与「不存在」，给出不同的引导文案。

③ 集市扫码授权（SSE 通道）

  • 实现：/api/auth/sse/qr/* 与 /api/auth/sse/oauth/callback 走集市侧二维码，回调后取集市身份并关联。
app.get("/api/auth/sse/qr/status", handlers::sseQrStatus);

会话与设备

① 会话列表

  • 用户操作：设置页看到所有登录设备（浏览器 / 系统 / 最近活跃 / 是否当前设备）。
  • 实现：会话存在 Redis（session:*），列表时扫描并解析，只保留属于当前用户的条目，按活跃时间排序。
// backend/src/app/handlers_sessions.cpp
void sessionsList(const Request& req, Response& res) {
    User user;
    if (!authx::requireUser(req, res, user)) return;
    auto currentId = authx::sessionId(req);
    std::vector<SessionInfo> sessions;
    for (const auto& name : Cache::scan("session:*", 500)) {
        std::string raw = Cache::get(name);
        if (raw.empty()) continue;
        SessionInfo info;
        if (!parseSession(name, raw, info) || info.userId != user.id) continue;
        info.current = currentId && info.id == *currentId;
        sessions.push_back(info);
    }
    std::sort(sessions.begin(), sessions.end(), ...);
}
  • 坑：scan("session:*", 500) 有 500 条上限。用户会话数一般远小于这个值，但全站会话多时扫描成本高，因此只能用于「用户自助查看」，不能做统计口径。

② 退出指定设备 / 退出其他设备

  • 实现：单条删除用会话 ID；「退出其他所有」遍历该用户会话，跳过当前会话逐个删。
void sessionRevokeOthers(const Request& req, Response& res) {
    User user;
    if (!authx::requireUser(req, res, user)) return;
    auto currentId = authx::sessionId(req);
    long long revoked = 0;
    for (const auto& name : Cache::scan("session:*", 500)) {
        std::string raw = Cache::get(name);
        if (raw.empty()) continue;
        SessionInfo info;
        if (!parseSession(name, raw, info) || info.userId != user.id) continue;
        if (currentId && info.id == *currentId) continue;   // 保留当前会话
        deleteSession(info.id);
        ++revoked;
    }
    applog::access("[session] user=" + user.id + " revoked_others=" + std::to_string(revoked));
}
  • 坑：必须显式跳过当前会话，否则用户点「退出其他设备」会把自己也踢下线。
  • 面试点：会话吊销只删服务端记录，令牌本身仍可能有效到过期。若要求「立即失效」，令牌校验必须每次回查会话，或维护吊销名单。

③ 资料与头像

  • 实现：PUT /api/me/profile 改资料；GET/POST /api/me/avatar 上传与读取头像，user-avatar 服务处理裁剪与缓存。
app.put("/api/me/profile", handlers::accountUpdateProfile);
app.get("/api/me/avatar", handlers::avatarGet);

OAuth2 与 OIDC

① 授权上下文

  • 用户操作：第三方应用跳过来后，先看到「XX 应用请求以下权限」。
  • 实现：GET /api/oauth/authorize/context 按 client_id 返回应用信息与 scope 列表，用于渲染同意页。
app.get("/api/oauth/authorize/context", handlers::oauthContext);

② 授权与授权码

  • 用户操作：点同意 → 跳回应用，地址栏带 code。
  • 实现：校验 redirect_uri 白名单（精确匹配）→ 校验 PKCE 参数形态 → 生成随机 code 存 Redis（带 TTL）→ 302 回跳并附 state。
// backend/src/app/handlers_oauth.cpp
bool validPkce(const std::string& challenge, const std::string& method) { ... }

std::string issueCode(const std::string& clientId, const std::string& userId,
                      const std::string& redirectUri, const std::string& scope,
                      const std::string& challenge, const std::string& method,
                      const std::string& state, const std::string& nonce) {
    std::map<std::string, JsonValue> data;
    data["client_id"] = JsonValue(clientId);
    data["user_id"] = JsonValue(userId);
    data["redirect_uri"] = JsonValue(redirectUri);
    data["scope"] = JsonValue(scope);
    data["code_challenge"] = JsonValue(challenge);
    data["code_challenge_method"] = JsonValue(method);
    data["state"] = JsonValue(state);
    data["nonce"] = JsonValue(nonce);
    std::string code = util::randomToken(32);
    Cache::set("auth_code:" + code, jsonx::dump(data), AppConfig::get().authCodeSeconds);
    return code;
}
  • 坑：redirect_uri 必须精确匹配注册值。做前缀匹配等于允许攻击者把 code 引导到自己域名下的任意路径。
  • 坑：code 只能消费一次。consumeCode 要在读取后立即删除，先读后删的写法在并发下会被兑换两次。

③ 换取令牌

  • 用户操作：无感知（应用后端完成）。
  • 实现：grant_type=authorization_code 时依次校验 code 有效性 → client 身份 → redirect_uri 一致 → PKCE（BASE64URL(SHA256(verifier)) 与 challenge 常数时间比较）→ 签发 access / refresh / id_token。
bool verifyPkce(const std::string& verifier, const std::string& challenge) {
    if (verifier.empty()) return false;
    return util::constantTimeEquals(util::base64UrlEncode(util::sha256Raw(verifier)), challenge);
}

void oauthToken(const Request& req, Response& res) {
    std::string grantType = http::input(req, "grant_type");
    ...
    if (grantType == "authorization_code") {
        auto data = consumeCode(code);
        if (!data) { oauthError(res, 400, "invalid_grant", "authorization code invalid or expired"); return; }
        if (clientId != codeClient) { oauthError(res, 400, "invalid_grant", "client mismatch"); return; }
        auto app = repo::findApplicationByClientId(codeClient);
        std::string clientError;
        if (!verifyClient(*app, clientSecret, clientError)) { oauthError(res, 401, "invalid_client"); return; }
        if (!redirectUri.empty() && redirectUri != codeRedirect) {
            oauthError(res, 400, "invalid_grant", "redirect_uri mismatch"); return;
        }
        ...
    }
}
  • 面试点：PKCE 的比对要用常数时间比较。普通 == 在理论上可被逐字节探测，虽然 PKCE 的 challenge 本身不是秘密，但统一用常数时间比较是惯例。

④ userinfo 与 introspect

  • 实现：/api/oauth/userinfo 按 Bearer access_token 返回 claim；/api/oauth/introspect 供资源服务器校验令牌（先校验调用方 client 身份，再判断令牌是否有效并返回 active）。
void oauthIntrospect(const Request& req, Response& res) {
    auto app = repo::findApplicationByClientId(clientId);
    std::string clientError;
    if (!app || !verifyClient(*app, clientSecret, clientError)) {
        oauthError(res, 401, "invalid_client"); return;
    }
    std::map<std::string, JsonValue> obj;
    obj["active"] = JsonValue(false);       // 默认无效，只有校验通过才置 true
    if (token.empty()) { http::json(res, 200, JsonValue(obj)); ... }
}
  • 坑：introspect 的默认值必须是 active=false。默认 true 再逐项排查，任何分支遗漏都会变成「伪令牌通过校验」。

⑤ 发现文档与 JWKS

  • 实现：/.well-known/openid-configuration 返回各端点与 jwks_uri；/.well-known/jwks.json 返回 RSA 公钥（RsJwt::jwks()），带 5 分钟缓存。
void oidcJwks(const Request&, Response& res) {
    res.statusCode = 200;
    res.body = RsJwt::jwks();
    res.headers["Content-Type"] = "application/json; charset=utf-8";
    res.headers["Cache-Control"] = "public, max-age=300";
}
  • 面试点：内部会话 JWT 用 HMAC（单一密钥、单服务校验），对外的 OIDC id_token 用 RSA（多方验签、公钥公开）。两种令牌用途不同，密钥体系也不同。

⑥ 机器对机器接口

  • 实现：password/verify、session/verify、session/revoke、users/list、developer/update 走 client 凭证（Basic 或表单），由 m2mAuthorized 统一鉴权。
bool m2mAuthorized(const Request& req, Response& res, std::string& clientId, bool developerWrite = false) {
    std::string clientSecret = http::input(req, "client_secret");
    auto basic = basicCredentials(req);
    if (clientId.empty()) clientId = basic.first;
    if (clientSecret.empty()) clientSecret = basic.second;
    auto app = repo::findApplicationByClientId(clientId, true);
    ...
}
  • 坑：developerWrite 区分读写权限。同一个 client 凭证不应同时具备「查用户」和「改开发者信息」的能力。

应用与授权管理

① 应用注册与审核

  • 用户操作：第三方提交应用申请（名称、回调地址、scope）→ 管理员审核 → 通过后拿到 client_id / secret。
  • 实现：/api/apps/apply 建申请，/api/apps/pending 列待审，/api/apps/{id}/review 审核；内接应用由管理员直接建（/api/apps）。
app.post("/api/apps", handlers::appsCreate);        // 内部应用
app.post("/api/apps/apply", handlers::appsApply);   // 第三方申请
app.get("/api/apps/pending", handlers::appsPending);
app.post("/api/apps/{id}/review", handlers::appsReview);
app.post("/api/apps/{id}/reset-secret", handlers::appsResetSecret);
  • 坑：重置 secret 后旧 secret 必须立即失效，并清理该应用的现有令牌。只换 secret 不吊销令牌，等于给了旧凭证继续使用的窗口。

② 授权同意记录

  • 用户操作：「我的授权」里看到授过哪些应用，可撤销。
  • 实现：consents 表按「用户 + 应用」记一条，撤销后该应用下次访问需重新同意。
app.get("/api/consents", handlers::consentsList);
app.put("/api/consents/{id}", handlers::consentsUpdate);
app.del("/api/consents/{id}", handlers::consentsRevoke);

③ 外部身份绑定

  • 实现：/api/identities 只提供列表与解绑；绑定入口被刻意关闭，身份只能通过一次校验过的集市 OAuth 回环建立。
app.get("/api/identities", handlers::identitiesList);
// Legacy POST /api/identities 已停用：身份只能通过校验过的集市 OAuth 回环绑定
app.del("/api/identities/{id}", handlers::identitiesUnbind);
  • 面试点：开放「直接 POST 绑定」等于允许把任意邮箱绑到自己账号，等于账号接管。绑定必须证明「你确实拥有那个身份」，所以只能走 OAuth 回环。

④ 首页应用展示

  • 实现：homepage-apps 公开列表 + 管理员 CRUD + 图标上传，用于落地页展示生态应用。
app.get("/api/public/homepage-apps", handlers::homepageAppsPublic);
app.post("/api/admin/homepage-apps", handlers::adminHomepageAppsCreate);
app.post("/api/admin/homepage-apps/{id}/icon", handlers::adminHomepageAppsIcon);

后台与可观测

① 用户管理

  • 实现：管理员可增删改查用户；删除走停用，物理删除会打断外键引用。
app.get("/api/admin/users", handlers::adminUsersList);
app.post("/api/admin/users", handlers::adminUsersCreate);
app.put("/api/admin/users/{id}", handlers::adminUsersUpdate);
app.del("/api/admin/users/{id}", handlers::adminUsersDelete);

② 日志

  • 实现：前端把客户端日志打到 /api/logs/client；管理员可列日志文件与查看末尾若干行；服务端另有访问日志（applog::access）。
app.post("/api/logs/client", handlers::clientLog);
app.get("/api/admin/logs", handlers::adminLogsList);
app.get("/api/admin/logs/{file}", handlers::adminLogsTail);
  • 坑：/api/admin/logs/{file} 的文件名必须做白名单或路径归一化。直接拼接路径，..%2F 就能读任意文件。

③ 存储不可用的统一降级

  • 实现：所有依赖存储的 handler 包一层 storageAware，捕获 StorageUnavailable 后统一返回 503 并给 Retry-After。
// backend/src/app/routes.cpp
auto storageAware(void (*handler)(const Request&, Response&)) {
    return [handler](const Request& req, Response& res) {
        try {
            handler(req, res);
        } catch (const StorageUnavailable&) {
            http::error(res, 503, "temporarily_unavailable", "身份服务暂时不可用，请稍后重试");
            res.headers["Retry-After"] = "3";
        }
    };
}
  • 面试点：把「存储故障」建模成一种异常类型，在路由层统一转成 503，比在每个 handler 里写 try-catch 更可靠 —— 新增接口不会漏。

UniSSO · 面试速答

  • 注册：验证码 HMAC 后存 Redis，按邮箱摘要与 IP 双限流，待验证态与正式用户分离。
  • 登录：本地 bcrypt 优先，失败且标识为邮箱时回退集市校验；锁定键 = 邮箱 + IP。
  • 扫码：二维码记录带 TTL，确认接口按用户限流，过期返回 410，已处理返回 409。
  • OAuth2：redirect_uri 精确匹配、code 一次性、PKCE 常数时间比对、introspect 默认 active=false。
  • 两种令牌：内部会话 HMAC JWT，对外 OIDC id_token RSA + JWKS。
  • 会话：Redis session:*，支持看设备、踢单台、踢其他所有；吊销只删服务端记录，需即时失效则要回查。
  • 边界：只管身份，应用内角色、用户组、资源权限归各应用。
