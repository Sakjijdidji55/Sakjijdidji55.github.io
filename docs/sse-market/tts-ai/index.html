11 TTS 与 AI 研究

3 分钟读完 · 1,057 字

ai-infra 的两块能力：语音合成（Voice Studio）与文本模型服务化，统一由 API 开放平台对外。

仓库说明：TTS 与研究侧为内部服务，没有公开仓库。本章的接口与协议来自两处可核验的对接实现 —— 小程序平台的 src/routes/tts.js（同源代理）与集市云的 GPU Pod / vLLM 部署方式；内部实现细节不做推测。

服务形态

① 对外形态

  • 域名：https://tts.ssemarket.cn。
  • 鉴权：请求头 X-API-Key，Key 只存在服务端环境变量，不下发前端。
  • 超时：代理侧 70 秒（合成可能排队，短超时会把正常任务判成失败）。
// applet/src/routes/tts.js
/**
 * Voice Studio（TTS）代理。
 *
 * API Key 只存在服务端环境变量 MP_TTS_API_KEY，小程序页面调用同源 /v1/tts/*，
 * 不接触也不暴露 Key。这里只转发合成/音色/任务接口，并做简单限流。
 */
const BASE = () => String(process.env.MP_TTS_BASE || 'https://tts.ssemarket.cn').replace(/\/+$/, '');
const KEY = () => String(process.env.MP_TTS_API_KEY || '');

async function upstream(pathname, init = {}, timeoutMs = 70000) {
  const key = KEY();
  if (!key) throw new ApiError(503, 'TTS_NOT_CONFIGURED', '语音合成服务尚未配置');
  const headers = new Headers(init.headers || {});
  headers.set('X-API-Key', key);
  return fetch(`${BASE()}${pathname}`, { ...init, headers, signal: AbortSignal.timeout(timeoutMs) });
}

② 由小程序平台代理的原因

  • 前端拿不到 Key：页面只调同源 /v1/tts/*，Key 在服务端注入。
  • 可限流：代理层按 IP 做令牌桶（默认 30 次 / 60 秒），不同接口各自命名桶。
  • 可降级：未配置 Key 时返回 503 TTS_NOT_CONFIGURED，前端不必等到超时。
async function limit(ctx, name, capacity = 30, windowSeconds = 60) {
  await enforce(ctx.services.limiter, { name: `tts-${name}`, subject: ctx.ip, capacity, windowSeconds });
}
  • 坑：代理必须设「上游超时 + 自身超时」两级。只设一级，上游卡住时连接会一直挂着，最终耗尽代理的连接池。

接口

① 音色

GET /v1/tts/me                      当前 Key 对应的账号信息与额度
GET /v1/tts/base-models             可用的基础模型
GET /v1/tts/voices                  我的音色列表
GET /v1/tts/voices/:runId/sample    试听某个音色
  • 实现：base-models 与 voices 分离 —— 前者是「能训练出什么音色」的底座，后者是「已经训练好的」。列表与试听分开，避免列表接口返回音频二进制。

② 合成

  • 用户操作：选音色 → 输文本 → 合成 → 轮询任务 → 试听/下载。
  • 实现：POST /v1/tts 提交合成任务，返回 jobId；音频通过独立端点拉取，避免把二进制塞进 JSON。
POST /v1/tts                      提交合成，返回 jobId
GET  /v1/tts/tasks/:jobId         查任务状态
GET  /v1/tts/tasks/:jobId/audio   取音频流

async function forwardAudio(ctx, res) {
  const buffer = Buffer.from(await res.arrayBuffer());
  ctx.res.statusCode = res.status;
  ctx.res.setHeader('Content-Type', res.headers.get('content-type') || 'audio/wav');
  ctx.res.setHeader('Cache-Control', 'no-store');
  const jobId = res.headers.get('x-job-id');
  ...
}
  • 坑：音频响应要带 Cache-Control: no-store。合成结果与账号绑定，被 CDN 或浏览器缓存后可能被他人取到。
  • 面试点：音频走独立端点；base64 内联会让响应体积膨胀 33%，也无法流式播放。

③ 歌曲与翻唱

GET  /v1/tts/songs                 歌曲列表
GET  /v1/tts/covers                翻唱列表
POST /v1/tts/covers                提交翻唱任务
GET  /v1/tts/covers/:coverId       翻唱详情
GET  /v1/tts/covers/:coverId/audio 翻唱音频

  • 实现：翻唱是独立任务类型，与普通合成共用任务查询与音频下发，但有自己的列表与详情，因为参数（原曲、音高、音色）更多。

  • 坑：翻唱属于用户生成内容，需要保留原始素材与生成结果的关联，便于下架时一并处理。

运行环境

① GPU Pod 承载

  • 实现：TTS 与文本模型都跑在集市云的 GPU Pod 上，进程由 supervisord 托管，崩溃自启、开机自启。
YatTerra GPU Pod（namespace clouds）
  └─ supervisord
       ├─ GPT-SoVITS（TTS）
       └─ vLLM（文本模型）
  • 坑：TTS 与 vLLM 共享同一张卡时，要靠 MPS 百分比切分。不切分就是「谁先占满显存谁赢」，另一个服务随机 OOM。

② 文本模型服务化

  • 实现：文本模型统一由 vLLM 承载，靠三个机制吃满 GPU：
PagedAttention   KV Cache 分页管理，避免显存碎片
连续批处理       请求动态进出批次，不等最慢的那个
前缀缓存         相同系统提示词复用 KV，省去重复计算
  • 面试点：前缀缓存对「固定系统提示 + 变长用户输入」的问答场景收益最大；如果每次提示词都不同，命中率会接近 0。

③ 压测记录

  • 来源：内部压测记录（4B 量级模型，单卡 24GB）。
峰值      7.6k tok/s @ 384 并发
推荐区间  128–256 并发：6.4k–7.4k tok/s，TTFT 2–3.4s
上下文    128k，前缀缓存命中率约 61.5%
  • 面试点：结论给「推荐区间」。峰值并发下 TTFT 与成功率都会劣化，按峰值配置容量等于把系统长期置于过载边缘。

评测与研究

① 三类实测

并发梯度     固定输入长度，逐级提升并发，找吞吐与延迟的拐点
长上下文     128k 输入下的显存占用与速度衰减
工具调用     Agent 场景下模型选工具、填参数的成功率

② 指标口径

吞吐（tok/s） / TTFT（首 token 延迟） / 成功率 / 前缀缓存命中率
  • 面试点：TTFT 比吞吐更贴近体感。用户感知的是「多久看到第一个字」，整段生成速度是次要指标。

③ 模型矩阵

  • 包含：多模态对话、轻量 LLM（工具调用 / 思考链）、视频生成、向量检索与重排、TTS。

  • 说明：矩阵的具体成员与版本随发布变化，接入方以 API 开放平台的 /v1/models 返回为准，不硬编码模型名。

TTS 与 AI · 面试速答

  • 形态：tts.ssemarket.cn + X-API-Key，前端不接触 Key，由小程序平台同源代理并限流。
  • 接口分层：音色（base-models / voices）→ 合成（提交任务）→ 任务（状态）→ 音频（流式下载）。
  • 运行环境：GPU Pod + supervisord；文本模型用 vLLM（PagedAttention / 连续批处理 / 前缀缓存），与 TTS 共卡时靠 MPS 切分。
  • 容量结论：按推荐并发区间配置，不按峰值。
  • 口径：TTFT 优先于吞吐；模型名不硬编码，以 /v1/models 为准。

代码与配置均取自各仓库实现，为便于阅读做了删减；版本迭代后以仓库为准。
