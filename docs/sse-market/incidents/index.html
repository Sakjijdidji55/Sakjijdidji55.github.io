13 事故复盘

9 分钟读完 · 3,757 字

这一章收了九起有记录的事故，从 2023 年上线到现在。每起按「现象、排查、根因、恢复、之后补了什么」写，最后收一张对照表和几条能带走的结论。

先说一个共同点：九起里面，没有一起是监控先发现的。发现的人分别是用户、同学、值班的人自己。

九次事故一览

# 时间 表象 谁先发现 根因类型
1 2023.9.18 站点起不来 上线当天的访问者 现场被重启冲掉，查不出
2 2023.9.22 13:45:12 全部帖子消失 用户反馈「帖子好像没了」 破坏性操作没有边界判断
3 2023.9.26 列表评论数全是 1 用户截图 派生字段取值错
4 2024.1.26 注册量静默归零 一位同学说收不到验证码 配置写错，且无告警
5 2025.11—2026.1 Redis 内存打满；随后 MySQL 磁盘打满 服务不可用后人工发现 无 TTL 清理策略；清理 SQL 写错列名
6 2026.8.30 整机挂死约 1 小时 用户反馈 四类「只进不出」的资源把磁盘吃到 97%
7 2026.9.19 主站 API 全量失效约 35 分钟 用户反馈 蜜罐把入口 Nginx 当扫描器，封了全部端口 7 天
8 2026.9.22 图床不可用约 20 小时，丢约 900 张图 部署时人工发现 蜜罐自锁 + 「失败即删组」逻辑 + 对象存储密钥从未生效
9 2026.9.29 25 个域名 HTTPS 全挂约 2.5 小时 用户反馈 k3s 重启后 traefik 按出厂值抢占 80/443

一、2023.9.18：上线当天，服务器崩溃

正式上线当天，站点打不开。值班的人直接重启，重启后重新部署，站点恢复了，原因没查出来。

没查出来的原因很具体：当时没有完整日志，重启把现场清掉了 —— 进程状态、错误栈、那一刻的请求，全在内存里，重启即丢失。这一次之后才补上日志系统，后面几次排查都靠它。

这起事故留下的结论只有一条：重启负责恢复服务，定位原因要靠现场。要重启之前，先把日志、堆栈、连接数、慢查询留下来。

二、2023.9.22 13:45:12：全部帖子被删除

上线第四天，有人反馈「帖子好像没了」。第一反应是数据库挂了，查下来库还在，帖子确实没了。

MySQL 的 general log 里，13:45:12 有一条把帖子全删的语句；后端日志在同一时刻连续出现多条删除帖子的请求。两条时间戳对上，结论是：正常请求打到了有缺陷的代码，日志里没有外部攻击的痕迹。组里另一个人用「删除一个本来就不存在的帖子」去测，必现全表被清空 —— 删除函数没有校验目标是否存在，传入不存在的 ID 时删除条件失效，语句退化成无条件删除。

数据靠 binlog 救回来。定位到 binlog.000003 的 Pos 217032，用 mysqlbinlog 按时间点和位置截出事故前的一段，再用 binlog2sql 解析成回滚 SQL 灌回数据库，最后核对帖子数与时间戳，确认没把事故之后的脏数据带回来。之后补了数据库备份，也把函数改成先判存在再删。

这起事故的教训是破坏性操作的写法：入参要校验（ID 大于 0 且目标存在），WHERE 必须命中主键，执行后校验影响行数（RowsAffected 只能是 1）。线上要假设参数是错的，尤其是 ID。binlog 是最后一道防线，前提是 ROW 格式和足够的保留期。

三、2023.9.26：列表里的评论数全变成 1

帖子列表每一条的评论数都显示 1。数据和评论都还在，问题出在列表查询：取到的是某一条评论记录，帖子的评论条数没有被统计。

修法是把列表计数改成按帖子聚合，或者单独维护计数字段。这也定下一条规矩：评论数、点赞数、浏览数这类派生字段必须有唯一事实源 —— 要么查询时聚合，要么写时维护加回填任务，不能顺手 join 一行当计数。

四、2024.1.26：邮箱验证码发不出去

注册量本来是每天一两个地涨，有一天开始连续几天为零，当时以为是确实没人注册。后来有同学说收不到验证码，才知道注册入口已经断了，只是一直没人报障。发现时已经到期末，手上任务也多，一直拖到 1 月 26 日才修。

修复本身很小：发送方式改成 TLS，发件箱换成企业邮箱。根因是端口 —— 把 465 写成了 456，而 QQ 邮箱已经关掉非 TLS 端口，连不上，验证码自然发不出。

这起事故的代价在发现环节：发信失败没有告警，注册为零也没有告警，两个沉默叠在一起，问题存在了几周。零值是最该报警的信号 —— 注册 0、发帖 0、消费 0，都值得一个告警。

五、2025.11：双 Token 改造，先撑爆 Redis，再撑爆 MySQL

2025 年 11 月 16 日，登录从单 token 改成双 token：短期 access token 加 30 天的 refresh token，refresh 用过一次即作废。改动本身没问题，问题在存储方式 —— refresh token 被写进 Redis，键名是 refresh_token:<JWT>，值是用户 ID，TTL 30 天，等这个 token 被用掉才 DEL。

于是每次登录、每次刷新都会写一个新键，键名本身是一整串 JWT（几百字节），30 天内不会消失。换设备、重复登录、微信里跳转重新授权，都在产生新键；没被用掉的 token 永远不删。Redis 内存一路涨，直到打满，登录链路整体不可用。

11 月 19 日，refresh token 改存 MySQL：新建 refresh_tokens 表（user_id、唯一的 token、expires_at、is_used、created_at），刷新时按 token、用户、未使用三个条件查一条，查到就标记为已使用再发新的一对；同时加了一个每 48 小时跑一次的清理任务，删掉三天前已使用的记录。

到这里本该结束，但清理任务的删除条件写错了列名：is_used = 1 AND updated_at < cutoff，而这张表和模型里只有 created_at，没有 updated_at。SQL 每次执行都报错，错误被 if result.Error != nil 接住，只打一行日志就返回 —— 任务「跑了」，一条没删。两个月后，MySQL 磁盘被这张表涨满。

2026 年 1 月 20 日的提交把它改成 created_at < cutoff，清理才真正生效。一行列名，两起事故：一次是 Redis 没有清理策略，一次是清理策略写错了也看不出来。

这起事故留下的两条：一是会话类数据要么有过期机制、要么有清理任务，两者都没有就是定时炸弹；二是清理任务必须验证真的删掉了 —— 看日志里「清理了 N 条」的 N，不要只看任务有没有被调度。

六、2026.8.30：磁盘满，整机挂死约一小时

20:26 起，机器上所有依赖磁盘的服务开始集体超时，日志落盘延迟三到七分钟；20:35 整机失去响应，硬挂死。

根因是四类「只进不出」的资源长期只增不减：每日 mysqldump 备份没有轮转，三年攒了 1178 个文件、14G；Docker 构建缓存没有清理，561 次构建留下 28.9G，而每日清理脚本因为文件丢失已经静默失败数月；容器日志没有上限，一个错误循环的容器单独占了 5.5G；journald 也没有上限，frps 和 k3s 每天多出 500M 以上。事发时磁盘水位 97%，只剩 7.9G。水位到顶之后，多路大 I/O 把系统级 I/O 拖停，最后整机挂死。

恢复过程里最麻烦的一步在重启之后：宿主机上那套空的默认 nginx 抢占了 80/443，入口容器起不来。后来把宿主机 nginx 永久停用，80/443 归入口容器唯一所有。

之后落地的机制：cron 重建每日维护脚本（构建缓存保留 72 小时、备份压缩保留 30 天、60 天后删）、journald 上限 1G、容器日志 50m×3、磁盘使用率 85% 告警。最大的教训是清理任务要验证真的在跑 —— 静默失败几个月没人发现，比没有清理更危险。

七、2026.9.19：蜜罐把入口 Nginx 封了，API 全量失效约 35 分钟

现象是主站 API 全线不可用，但后端进程活着，日志里有「服务就绪」，没有 panic 也没有 OOM，宿主机直连同一容器返回 200、耗时 1.7ms。数据库和 Redis 也都正常。

问题出在入口。蜜罐脚本按 IP 聚合 frps 连接来识别扫描器，而入口 Nginx 在七天内访问了四个代理共 1011 次，正好同时命中「四个以上代理 + 一千次以上」的 multi-scan 阈值 —— 反代的流量特征和扫描器在特征空间里几乎分不开，调阈值治不了本。致命的是执行动作：tarpit 封禁没有加 --dport，封的是全部端口，Nginx 发往任何后端的请求都被改道到 endlessh；叠加封禁 7 天，不处理就是一周故障。另外免名单是逐 IP 手写的静态列表，容器 IP 随重建变化，必然过时。

修复的做法是给脚本加内网网段豁免（127/8、10/8、172.16/12、192.168/16），利用脚本里「豁免 IP 已封则自动解封」的分支自愈，30 秒内业务恢复。没有手工解封，也不需要某个人在场。这个改法可以复现，不依赖某个人在场。

排查上留了一个可复用的判断方法：上游返回垃圾时，先去连一个肯定没人监听的端口，正常应该 Connection refused；如果那个端口也吐随机 token，五秒钟就能判定请求被按源 IP 在网络层劫持了，跟后端无关。

八、2026.9.22：图床部署失败，线上组被误删，丢约 900 张图

图床部署失败，平台随后把线上组删了，组目录随组清空，丢约 900 张图。这是九起里唯一丢数据的一次。

三个根因叠在一起。第一层是自锁：部署机通过 hairpin NAT 访问自己的域名时，源 IP 就是自己的公网 IP，而 SSH 蜜罐没有配 ignoreip，七天全端口 tarpit 把平台通往跳板机的路掐死了，包传不上去。第二层是自毁：部署平台的兜底逻辑是「新建的 pod 部署失败就释放」，而它把一次瞬时查询错误误判成「组不存在」，于是标记为新建，部署失败后真把线上组删了，审计记录里这种事发生过四次。第三层是没有备份：图床当时只有「写 MinIO」和「写本地磁盘」两种互斥模式，容器启动脚本用 su -l（login shell）拉起 supervisord，-l 重置了继承的环境变量，MinIO 密钥在应用进程里是空的，数据一路写本地盘，天生没有备份。

修复分两路：图床切到对象存储并做端到端验证（把本地文件移走仍然能出图，此后删组不再丢数据）；平台修掉误删判定逻辑。教训有两条：数据相关变更必须灰度，新旧方式并行一段时间再切换；删除类操作的条件如果依赖一次网络查询，不能凭一次判断就执行。

九、2026.9.29：traefik 抢了 80/443，25 个域名 HTTPS 全挂约 2.5 小时

16:30 开始，25 个域名陆续报证书错误，19:01 恢复。

根因是同一台机器上住着两套「看大门」的：docker 里的 nginx 有真证书、接真流量；k3s 自带的 traefik 零配置空跑。k3s 的出厂规矩是每次启动按出厂值重装自带组件，而 traefik 默认以 LoadBalancer 方式占用 80/443。此前的修复写在 k3s 托管文件 manifests/traefik.yaml 里，重启就会被覆盖 —— 隐患从装上 k3s 那天就存在。k3s 的 iptables 规则又插在表最前面，KUBE-SERVICES 先命中 443，docker 给 nginx 的规则永远轮不到。所以 nginx 没坏、证书也没过期，只是一个连接都没接到，这也解释了「直连容器 IP 正常、走域名报证书错」的反常现象。

触发点是一次 AI 运维代理的变更：为了启用 gVisor 执行 systemctl restart k3s，重启本身是必要的，但变更前没有留端口基线，没有复核「k3s 里没有业务，重启安全」这个前提，变更后也没有自检主站。变更「成功」了，主站已经挂了，靠人工报障拖了两个多小时。

最终修复是一个九行的 HelmChartConfig（traefik-config.yaml），k3s 会自动应用且重启不覆盖，把 traefik 固化成 ClusterIP —— 放弃对外端口，占位容器和 iptables 规则一起消失。

能带走的三条：

  1. 先保现场再动手。 重启、回滚、改配置之前，把日志、堆栈、连接、慢查询留下来。
  2. 破坏性操作当敌人对待。 校验、主键、影响行数、备份，四样缺一不可；删除条件依赖网络查询时，加二次确认或时间窗。
  3. 给「零」和「失败」配告警。 注册为零、发信失败、清理任务连续失败，都该有人被叫醒；等人来问坏没坏，代价太大。
